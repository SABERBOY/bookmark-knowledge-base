# Path to CoreCLR, 2026: Upgrade Guide - Technical Articles - Unity Discussions

[![Image 1: Unity 6 Roadmap Timeline](https://europe1.discourse-cdn.com/unity/optimized/4X/5/c/1/5c152f14a43420bc909eff7da30e1bc2fad6e45b_2_690x388.png)](https://europe1.discourse-cdn.com/unity/original/4X/5/c/1/5c152f14a43420bc909eff7da30e1bc2fad6e45b.png "Unity 6 Roadmap Timeline")

Over the course of 2026, Unity is planning changes that lead up to replacement of the scripting runtime in Unity 6.8, making CoreCLR the foundation of our C# layer. Unity 6.8 will no longer have Mono as an available option. This effort is broadly referred to as the **Path to CoreCLR.**

While we expect to use CoreCLR to bring code iteration time and runtime performance improvements over time, in Unity 6.8 we’re aiming for holistic performance parity - some things will be faster, others slower, on balance about the same.

This change will be largely source code compatible with existing projects, but there are some important breaking changes planned that we want game makers and Asset Store partners to be aware of.

This is a living document and will be updated on the road to Unity 6.8.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-latest-1)Latest!

The [Unity 7.0 alpha is now available](https://discussions.unity.com/t/unity-7-0-alpha-is-now-available/1738310), featuring the CoreCLR based Editor. This release exposes .NET Standard 2.1 / C#9. Some platforms have been migrated to the new .NET10-based BCL. We don’t anticipate significant performance differences against Mono based editors during the alpha period.

New areas of potential incompatibility between CoreCLR and Mono based execution environments have been added

*   Burst function pointer delegates must be public or internal
*   Throwing managed exceptions across native (Bursted) stackframes
*   String.GetHashCode
*   Locale specifiers

The Experimental CoreCLR Desktop Player is available as an installable component alongside the [Unity 6.7LTS Alpha](https://unity.com/releases/editor/alpha/6000.7.0a2?ampDeviceId=ce66bb48-6bfd-41c7-bf48-9cf5098d7b26&ampSessionId=1793953188609&ampTimestamp=1794039588617) starting with alpha 2.

The Experimental IL2CPP iOS Player is available as an installable component alongside the [Unity 6.7LTS Alpha](https://unity.com/releases/editor/alpha/6000.7.0a5?ampDeviceId=ce66bb48-6bfd-41c7-bf48-9cf5098d7b26&ampSessionId=1793953188609&ampTimestamp=1794039588617) starting with alpha 5.

This player is intended to allow users the ability to partially validate their projects against the upcoming CoreCLR changes in Unity 6.8. We strongly advise against using it for active game production.

*   The experimental player is **not supported**. It is included alongside the LTS, but won’t be part of normal LTS support policy. Bugs that don’t reproduce in the Mono player may or may not get fixed.
*   The experimental player provides the same .NET Standard 2.1 and C# 9 features as the Mono player. There will be no .NET 10 support in the experimental.
*   We don’t anticipate noticeable differences in performance from the experimental player and the Mono based player.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-net-10-api-and-behavioral-changes-2).NET 10 API and behavioral changes

Unity 7.0 will offer a .NET 10 based toolchain and BCL. This will be the only exposed Target Framework ([TFM](https://learn.microsoft.com/en-us/dotnet/standard/frameworks)). Precompiled assemblies targeting a TFM other than .NET Standard 2.1 may break in Unity 6.8.

Refer to Microsoft’s [.NET breaking changes](https://learn.microsoft.com/en-us/dotnet/core/compatibility/breaking-changes) documentation for general information about migrating between .NET versions.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-apis-removed-between-net-framework-47-and-net-10-3)APIs removed between .NET Framework 4.7 and .NET 10

Various .NET 4.7 APIs are not available in .NET 10. If your project is using any of these removed APIs, you will get compiler errors when opening your project in Unity 6.8.

You will need to manually fix these compiler errors before you can enter play mode.

In some cases, APIs have been removed from the core .NET profile, but moved to NuGet packages. For example, the `Microsoft.Win32.Registry` class was previously built-in to the .NET Framework, but is now offered via the `Microsoft.Win32.Registry` NuGet package. You can resolve errors involving APIs like this by adding the required NuGet packages to your project.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-floating-point-operations-4)Floating point operations

The new CoreCLR runtime is compliant with the IEEE 754 standard for floating point operations. This may be different from what Mono’s JIT produced, and so the results of floating point calculations may be a little different in some situations. See [https://github.com/dotnet/runtime/issues/34783](https://github.com/dotnet/runtime/issues/34783) for an example of this.

IL2CPP is not affected by this change. IEEE 754 compliance in IL2CPP builds is determined by the underlying compiler used to compile the generated C++ code, as in earlier versions. Burst-compiled code is also not affected; Burst is already IEEE 754 compliant when used with `FloatMode.Strict` (which is the default).

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-deprecation-of-binaryformatter-5)Deprecation of BinaryFormatter

The BinaryFormatter class has been [marked obsolete](https://learn.microsoft.com/en-us/dotnet/core/compatibility/serialization/8.0/binaryformatter-disabled) in .Net 10 due to [long-standing security and safety issues](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide). See the official [migration guide](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/).

If your project is using BinaryFormatter, we recommend replacing it with alternative APIs, such as:

*   `UnityEngine.JsonUtility`
*   `System.Runtime.Serialization.DataContractSerializer`
*   `System.Text.Json.JsonSerializer`
*   `System.IO.BinaryReader and System.IO.BinaryWriter`

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-manageddebugger-api-removal-6)ManagedDebugger API removal

The [`UnityEditor.Scripting.ManagedDebugger`](https://docs.unity3d.com/ScriptReference/Scripting.ManagedDebugger.html?ampDeviceId=ce66bb48-6bfd-41c7-bf48-9cf5098d7b26&ampSessionId=1793953188609&ampTimestamp=1794039588617) API is not supported under CoreCLR.

To fix this issue, use the `System.Diagnostics.Debugger` API instead.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-static-initialization-order-7)Static initialization order

Calls to static constructors now happen when a type’s data or static fields are first used, rather than when methods in the type are first JITted. This may result in changes to the order in which static constructors are called, or may result in static constructors which were previously called on the main thread being called on background threads instead.

If you need to ensure that a static constructor has run by a particular point in your code, you can use the lifecycle APIs to mark up the constructor to be called at the appropriate point in the code reload lifecycle, or use `System.Runtime.CompilerServices.RuntimeHelpers.RunClassConstructor()` method to force the runtime to call the static constructor immediately if it has not already done so.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-more-strict-type-accessibility-constraints-8)More strict type accessibility constraints

The CoreCLR runtime more strictly enforces type accessibility rules (`public`, `internal`, etc) at runtime. For example, calling a private method from outside of the declaring class is not legal in C#; this is usually blocked by the compiler, but it is possible to create situations where it happens, e.g. when a method in a precompiled assembly is called by a method in another precompiled assembly, and that method is then changed from public to private. Mono would throw `MethodAccessException` for some of those situations, but not all of them; CoreCLR is more strict, so you may see `MethodAccessExceptions` be thrown in situations where it previously was not.

This does not affect access to private members via Reflection APIs.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-overflow-checks-in-system-types-9)Overflow checks in System types

Many system types now use [`checked` statements](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/checked-and-unchecked) in conversion methods and operators, meaning that they may throw `OverflowException` exceptions in cases that previously did not. For example, `IntPtr.ToInt32()` will now throw an `OverflowException` when called on 64-bit platforms, because it is not possible to fit a 64-bit pointer into a 32-bit integer without overflowing.

To fix this issue, rewrite your code to avoid overflows, or catch the `OverflowException` and handle it.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-fewer-text-encodings-registered-by-default-10)Fewer text encodings registered by default

.Net 10 only registers [a limited set of text encodings](https://learn.microsoft.com/en-us/dotnet/api/system.text.codepagesencodingprovider?view=net-8.0) by default compared to .NET 4.7. ASCII and Unicode encodings are still available, but other encodings such as Windows-1252 are not registered by default. This means that using methods such as `System.Text.Encoding.GetEncoding()` with a less common encoding may throw a `NotSupportedException`.

You can solve this problem by switching to one of the common encodings, or by calling `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` to register the wider set of encodings offered by `CodePagesEncodingProvider`.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-mono-pinvoke-calls-no-longer-available-11)Mono P/Invoke calls no longer available

The Mono libraries such as `MonoPosixHelper.dll` are no longer shipped as part of Unity, and so code which directly calls into them using P/Invoke will no longer work. You will not get compiler errors from this, but calling the methods at runtime will throw `DllNotFoundException`.

To fix this issue, either stop using these methods, or obtain the necessary libraries from the Mono project and ship them as plugins within your project.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-code-reload-12)Code Reload

Unity no longer unloads and reloads the entire managed code space when applying code changes or when entering and exiting play mode. This means that static variables are no longer automatically reset. If the static variables hold references to types defined in assemblies that have been modified, this can also block those assemblies from being unloaded so that the modified versions can be loaded.

Unity offers a set of Editor Lifecycle callbacks that trigger at different points around code reload and entering/exiting playmode. There are two ways to use these callbacks to reset static variables:

1.   Apply the `[AutoStaticsCleanup]` attribute to the type, or static members of that type, which need cleaning up. Unity uses these attributes to automatically generate code that resets the static members when the appropriate Editor Lifecycle events are triggered.
2.   Write a static method which contains whatever logic you need, and bind it to one of the Editor Lifecycle events using an attribute on the method such as `[BeforeCodeUnloading]`.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-appdomaincurrentdomaingetassemblies-not-recommended-13)AppDomain.CurrentDomain.GetAssemblies not recommended

Use of the `AppDomain.CurrentDomain.GetAssemblies()` method is not recommended, as it may return assemblies which are in the process of being unloaded, causing errors or preventing code from reloading correctly. Unity will report warnings about use of this API.

Instead, change your code to use [`UnityEngine.Assemblies.CurrentAssemblies.GetLoadedAssemblies()`](https://docs.unity3d.com/6000.5/Documentation/ScriptReference/Assemblies.CurrentAssemblies.GetLoadedAssemblies.html?ampDeviceId=ce66bb48-6bfd-41c7-bf48-9cf5098d7b26&ampSessionId=1793953188609&ampTimestamp=1794039588617) to retrieve the list of assemblies that are currently loaded.

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-appdomaincurrentdomaindomainunload-no-longer-called-when-unloading-code-14)AppDomain.CurrentDomain.DomainUnload no longer called when unloading code

In Unity 6, the `AppDomain.CurrentDomain.DomainUnload` event would fire when code was about to be reloaded in the Editor, making it a suitable place to perform certain kinds of cleanup, like halting background threads. This event will no longer fire in Unity 6.8 because we do not unload the application domain when reloading code.

Instead, change your code to use the `[AfterCodeReloadSerialization]` attribute from the Lifecycle API. For example:

```
[Unity.Scripting.LifecycleManagement.AfterCodeReloadSerialization]

static void CleanupResources() {
  // Clean up resources here
}
```

## [](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279/2#p-7279285-hidden-references-in-container-storage-15)Hidden references in container storage

Container types that do not clear unused parts of their storage may hold references that keep objects alive, preventing the objects from being garbage-collected and potentially blocking code reload for the assemblies containing those objects.

For example, suppose your project has a custom stack type backed by an array like this:

```
public class CustomStack
{
  private T[] _storage;
  private int _count;

  public CustomStack(int capacity)  
  {  
    _storage = new T[capacity];  
    _count = 0;  
  }

  public bool IsEmpty => _count == 0;

  public void Push(T newItem)  
  {  
    _storage[_count++] = newItem;  
  }

  public T Pop()
  {  
    return _storage[--_count];
  }
}
```

The implementation of `Pop()` does not modify the `_storage` array at all. If T is a reference type, this means that the `_storage` array will continue to hold the references that were previously pushed, even when the stack appears to be empty (i.e. `IsEmpty` returns `true`). This means the objects cannot be collected by the garbage collector, and the assemblies that their types belong to cannot be unloaded.

To fix this issue, modify the method that removes the item to also reset the storage to its default value. For our example:

```
public T Pop()
{  
    T result = _storage[--_count];  
    _storage[_count] = default(T);  
    return result;  
}
```

Resetting the entry in the storage to its default value - which is `null` for reference types - ensures that no reference is held, and that the object can be garbage collected as expected.

The standard .NET container types all do this already, but be aware of some lower-level containers in the framework, such as `System.Buffers.MemoryPool<T>`, which does not clear memory buffers when they are returned to the pool. Make sure you manually clear the contents of a buffer before you return it to the pool.
