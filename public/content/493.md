The [Gameplay Ability System (GAS)](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-ability-system-for-unreal-engine) is a framework for organizing gameplay related values and behaviors in a way that provides convenient editing, data-driven interaction, state and behavior replication, and out-of-the-box debugging tools. GAS can be used to implement damage and health, dynamic weapon fire rates and reload speeds, change movement variables, enabling and disabling pawn capabilities, implement pawn-environment interactions and much more. These concepts are simple on their own but GAS is a great solution when something like damage needs to consider more complicated calculations involving damage modifiers, crit/hit/dodge chances, armor, damage types and resistance stats. GAS is used in Epic's own games including Fortnite: Save the World, Fortnite: Battle Royale, LEGO Fortnite Odyssey and LEGO Brick Life, so it's a feature rich and battle tested system.

In this tutorial we’ll go through many concepts in the Gameplay Ability System (GAS) and use them in a practical way. This is to get familiarized with the role of each asset type in GAS and how you can use them. By setting up an Attribute Set, a handful of Gameplay Effects, a Gameplay Ability with targeting and a Gameplay Cue you will have a simple ability working from start to finish: from input to attributes to gameplay logic to audiovisual feedback.

Everything covered here is relevant for both singleplayer and networked multiplayer projects.

We will implement a health and damage system that serves as a good foundation to customize and extend with your own game rules. We will cover:

*   Health and damage implemented as **Gameplay Attributes** in an **Attribute Set**.

*   Modifying health by applying a damage **Gameplay Effect**.

*   A health bar**UMG Widget**that responds to health changes.

*   A self-damaging **untargeted Gameplay Ability**.

*   Gameplay Effect **application blocking tags**: Ignoring damage when immune.

*   Gameplay Ability **activation blocking tags**: Not being able to act when silenced.

*   A **targeted Gameplay Ability**: ground targeted area of effect damage.

*   A **charged Gameplay Ability**: jumping higher the longer you hold a key.

*   A Gameplay Ability that reacts to **Gameplay Events**: a player can ‘spook’ another. The other player will jump up via a reactive ability.

*   Damage numbers spawned as UMG widgets by **Gameplay Cue Notifies**.

The end result will be a targeted AOE damage ability, with health bars reacting and scrolling combat text spawned for damage events.

## Project Setup

I recommend using GAS only in an Unreal Engine code project, because:

*   Gameplay attributes can only be defined in code. This may change in the future.

*   Some features like [listening for attribute value changes](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices#howshouldilistentoattributechanges?) require some setup in code.

*   [Customizing damage calculations](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices#howshouldiimplementdamagetypeslikefiredamage/fireresistance?) is easier achieved in code than in blueprint.

Working alongside a programmer is recommended, though after the initial attributes and damage formula setup designers can achieve much in GAS by themselves.

You can create a new Unreal Engine project with the Third Person Template or work directly in an existing project. If you use the template, make sure to use the C++ version of the template. This tutorial was written for Unreal Engine 5.5. In this tutorial, the project is based on the Third Person Template and is called “AbilitiesLab”.

### Enabling the GameplayAbilities Plugin

The Gameplay Ability System (GAS) is a plugin that comes with Unreal Engine. Enable it in the editor via Edit > Plugins and ticking the _Gameplay Abilities_ plugin’s checkbox, then restart the editor.

### Including Modules in Build.cs

Since we’re going to be writing C++ code with GAS, our game project must include GAS’s code modules. In your project’s ‘MyGame.Build.cs’ add GameplayAbilities, GameplayTags and GameplayTasks to the PublicDependencyModuleNames:

`public class AbilitiesLab : ModuleRules{	public AbilitiesLab(ReadOnlyTargetRules Target) : base(Target)	{		PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs; 		PublicDependencyModuleNames.AddRange(new string[] { …, "GameplayAbilities", "GameplayTags", "GameplayTasks" });	}}`

### The Ability System Component

Many of GAS’s features become accessible by adding an Ability System Component (ASC) to an actor. Any actor can have an ASC. For players there are a few options as to which actor class to place the ASC on. In this tutorial we’ll add it to the Character class, which gets us experimenting quickly and because that actor class is relevant for singleplayer and multiplayer, as well as players and bots. For multiplayer games we generally recommend adding it to the PlayerState. For more guidance on how to decide the best place for your ASC, read [Gameplay Ability System - Best Practices for Setup](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices).

You can choose to either add an ASC in an actor blueprint or in code, but I recommend doing this in code because having the ASC accessible in C++ comes with benefits. Some ASC features are only accessible in code, like listening for attribute changes.

It’s likely that at some point you will need to add functionality to the AbilitySystemComponent by overriding its virtual functions or adding game project specific helper functions. In preparation for this, create a subclass of AbilitySystemComponent ahead of time.

`UCLASS()class ABILITIESLAB_API ULabAbilitySystemComponent : public UAbilitySystemComponent{	GENERATED_BODY()};`

Then add the component to your character class. In this tutorial I've named the variable LabAbilitySystemComponent to incorporate the project title.

```
UCLASS()
class AAbilitiesLabCharacter : public ACharacter
{
	GENERATED_BODY()

public:
	AAbilitiesLabCharacter();
	
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = Abilities)
	TObjectPtr<class ULabAbilitySystemComponent> LabAbilitySystemComp;
```

`AAbilitiesLabCharacter::AAbilitiesLabCharacter(){	...	LabAbilitySystemComp = CreateDefaultSubobject<ULabAbilitySystemComponent>(TEXT("AbilitySystem"));}`

### Implementing IAbilitySystemInterface

It's good practice to let any actor class that has an AbilitySystemComponent implement the IAbilitySystemInterface. The reason for this is mainly performance and is explained in[GAS: Best Practices for Setup](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices-for-setup#whatistheiabilitysysteminterfaceinterfacefor?isitmandatorytoimplement?). Let your character class implement it as follows.

`#include "AbilitySystemInterface.h" UCLASS(config=Game)class AAbilitiesLabCharacter : public ACharacter, public IAbilitySystemInterface{	...	virtual UAbilitySystemComponent* GetAbilitySystemComponent() const override;};`

`UAbilitySystemComponent* AAbilitiesLabCharacter::GetAbilitySystemComponent() const{	return LabAbilitySystemComp;}`

### Setting the Owner and Avatar

The Ability System Component (ASC) can be used with any actor type: besides pawns it can also be given to inanimate objects such as (non-pawn) destructible building actors with health and shields. The ASC does need to know which actors it's working with: by design it needs to know who its **owner** and**avatar** are. These are provided by calling`InitAbilityActorInfo(OwnerActor, AvatarActor)` on the ASC. The owner is what persistently represents the player, bot or entity. The avatar is what physically represents it.

In this tutorial, we'll provide the character actor as both owner and avatar. In the actor's BeginPlay, call`InitAbilityActorInfo(this, this)` to let the ASC know that the character will be both its owner and avatar. For more information about the owner and avatar and when to set it, see[Best Practices for Setup - What is the OwnerActor of an ASC? What is the AvatarActor?](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices-for-setup#whatistheowneractorofanasc?whatistheavataractor?).

`void AAbilitiesLabCharacter::BeginPlay(){	Super::BeginPlay(); 	// Provide this character as owner and avatar	LabAbilitySystemComp->InitAbilityActorInfo(this, this);	...}`

For players, the ASC must be able to resolve the PlayerController from the owner actor. This is necessary for some ability features like targeting, and local prediction in networked games. The owner should either be the PlayerController itself, or a Pawn/Character or PlayerState that the ASC can use to find the PlayerController.

If the PlayerController is not resolvable yet from the ASC's owner - for example the pawn isn't possessed yet or in a networked game the PlayerController isn't replicated yet - you should call RefreshAbilityActorInfo later when the PlayerController is resolvable from the owner. The section [Best Practices for Setup - When should I call InitAbilityActorInto?](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices-for-setup#whenshouldicallinitabilityactorinfoforaplayer?) goes more in-depth on the PlayerController dependency.

## Introduction to Attribute Sets

Attribute Sets are classes that define a collection of attributes: numerical values like health, damage, movement speed that GAS can interact with by modifying values or using them to calculate other attributes. Game code can use those values directly, listen for changes or respond to thresholds being crossed like health reaching 0. Managing numerical values as GAS attributes comes with advantages, for example:

*   Picking attributes from dropdowns

*   Using attributes in GameplayEffects

*   Listening for attribute value changes via the ASC

*   Appearing in [GAS Debugging Tools](https://dev.epicgames.com/community/learning/tutorials/Y477/unreal-engine-gas-debugging-tools)

*   In networked projects: ease of replication, prediction and rollback

Attribute sets must be created in C++, because it’s currently not possible to define attributes via blueprint. Start by creating a subclass of UAttributeSet. Then define attributes by adding FGameplayAttributeData properties marked with the UPROPERTY() macro. For now we’ll be creating two attributes: Health and MaxHealth.

```
UCLASS()
class ABILITIESLAB_API ULabHealthAttributeSet : public UAttributeSet
{
	GENERATED_BODY()
	
public:
	// Current health
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Replicated)
	FGameplayAttributeData Health;
```

For networked games, mark any attribute that needs its values to be replicated to clients as Replicated. Then implement GetLifetimeReplicatedProps() as with any class with replicated properties. This step can be skipped for single-player games.

`#include "Net/UnrealNetwork.h" void ULabHealthAttributeSet::GetLifetimeReplicatedProps(TArray< FLifetimeProperty >& OutLifetimeProps) const{	Super::GetLifetimeReplicatedProps(OutLifetimeProps);	DOREPLIFETIME(ULabHealthAttributeSet, Health);	DOREPLIFETIME(ULabHealthAttributeSet, MaxHealth);}`

When you launch the editor, attribute set classes are found and their attribute properties are scanned and cached. In editor, wherever a FGameplayAttribute property is editable you can now select LabHealthAttributeSet.Health to choose an attribute. This is useful when creating GameplayEffects, but also generally to write game code that interacts with a variable attribute.

### Attribute Accessors and Initial Values

In general ‘accessors’ refer to getter and setter functions. In the source code for AttributeSet.h there is a useful macro ‘ATTRIBUTE_ACCESSORS’ that you can copy into your attribute subclass’s header file. This macro generates functions for the attribute set class to get, set and initialize an attribute value with simple function names based on your attribute name like GetHealth, SetHealth and InitHealth. There is also a getter for an attribute’s definition GetHealthAttribute() which is useful to test against in functions that get called with a variable attribute, demonstrated further down. Some more information about that macro [here](https://dev.epicgames.com/community/learning/tutorials/DPpd/unreal-engine-gameplay-ability-system-best-practices#whatistheattribute-accessorsmacrofor?).

Starting from UE 5.6 you won’t need to copy the macro. It is available immediately as ATTRIBUTE_ACCESSORS_BASIC.

Copy the following ATTRIBUTE_ACCESSORS macro definition to the top of your attribute set subclass’s header file.

`#define ATTRIBUTE_ACCESSORS(ClassName, PropertyName) \	GAMEPLAYATTRIBUTE_PROPERTY_GETTER(ClassName, PropertyName) \	GAMEPLAYATTRIBUTE_VALUE_GETTER(PropertyName) \	GAMEPLAYATTRIBUTE_VALUE_SETTER(PropertyName) \	GAMEPLAYATTRIBUTE_VALUE_INITTER(PropertyName)`

Then use the macro for each defined attribute like this inside the attribute set class declaration:

`UCLASS()class ABILITIESLAB_API ULabHealthAttributeSet : public UAttributeSet{	GENERATED_BODY()	…	ATTRIBUTE_ACCESSORS(ULabHealthAttributeSet, Health);	ATTRIBUTE_ACCESSORS(ULabHealthAttributeSet, MaxHealth);}`
